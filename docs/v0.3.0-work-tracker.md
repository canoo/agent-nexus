## Completion rule

For each issue, compare current behavior with every acceptance criterion.
Record its implementation commit, automated or manual verification, remaining
gaps, and first released version. Passing unrelated tests or merging adjacent
work does not satisfy an issue. Keep unreleased work under `Unreleased` in the
changelog. Closing issues remains a maintainer action.

## Executable native-host verification

Nine subprocess regressions exercise actual source extension envelopes, protocol
frames, Chrome/Edge launcher binaries, and isolated SQLite stores. They cover
accepted activity, disabled collection, revoked consent, resume/regrant boundaries,
sensitive-field rejection, browser mismatch, malformed JSON and oversized headers.
The 17 total host tests pass on Node 25 and minimum Node 22.13.

This is executable protocol integration, not a live Chrome/Edge extension test.
Computer-use inventory exposes no browser or app surfaces in this session.
Chrome's [native-messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)
requires a host response for `sendNativeMessage`. The launchers now flush exactly
one fixed acknowledgement and close input afterwards; the extension validates
that response. A regression holds stdin open and sends two batched frames,
verifying one response, one stored span and host exit. These launchers are
one-shot and do not support persistent `connectNative` ports. Live browser
permission, registration and GUI lifecycle verification remain open.

Latest automated evidence for the acknowledgement slice: 17 host tests,

Go build/vet/tests and MCP/desktop audits pass (zero vulnerabilities).
Node 22.13 compatibility checks include the host response lifecycle and Rust
